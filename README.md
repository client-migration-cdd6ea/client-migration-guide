<a id="backup"></a>
## 升级前要留下哪些可恢复记录

记录应用版本、内核版本、当前配置名称、策略选择，以及自己修改过的规则、脚本和接管设置。区分提供方生成的内容与自己的覆盖项：重新下载订阅未必能恢复手工设置。

若软件提供导出或备份，先读其备份范围说明，确认是否包含账号凭据、配置、规则与界面选项。将备份保存在自己的受保护设备中，并检查文件确实生成、大小合理且能被该软件识别。没有验证的空文件不能算备份。

不要把含密码、节点或私人订阅的备份提交到公开仓库。只记录必要信息，不导出整台设备的无关资料。关键工作、会议和上传未完成时，先不开始迁移。

<a id="compatibility"></a>
## 核对安装来源和兼容条件

在软件项目认可的发布渠道查看版本说明，核对系统最低要求、CPU 架构、内核变化和配置迁移提示。名称相似的安装包不一定属于同一项目，不从陌生镜像下载所谓兼容版。

有些字段或功能依赖具体内核，应用版本与内核版本应分别记录。不要仅看发布编号更大就推定所有旧配置兼容。若文档提到不可逆迁移或旧版本不能读取新数据，先保留独立备份并确认恢复办法。

安装遇到来源或证书警告时，停止并核实，不通过关闭安全防护继续。自己无法判断的驱动、权限或系统组件改动，按项目支持说明处理，不执行网友提供的不明修复脚本。

<a id="pilot"></a>
## 先迁移一台设备，不覆盖全部

优先选一台可暂时退出业务的设备验证。保持其他设备的已知可用状态，不同时把全部客户端升级，也不让两个会接管路由的版本同时运行。

按软件支持方式安装并导入配置，先不用额外脚本和复杂覆盖测试基本功能。依次验证启动、配置加载、策略显示、一个小请求和正常断开后的基础联网。每一阶段通过再继续下一项。

基本功能正常后，再逐项恢复自己的规则或设置，每加入一项就复测原任务。这样出现问题时能定位到具体改动，避免把所有覆盖项同时导入后无法判断来源。

换机时，确认新设备已正确读取私人地址和套餐允许的使用条件；不要直接复制未知用途的整个旧程序目录。迁移成功后，再按自己的需求处理旧设备，不提前删除唯一可用环境。

<a id="symptoms"></a>
## 升级后按症状处理

**应用无法启动：** 保存具体错误与系统版本，核对兼容要求和官方已知问题。不要立刻清空应用数据；先确认是否存在软件支持的修复或恢复流程。

**配置解析报错：** 记录字段名和报错阶段，核对新内核与订阅格式。先测试独立的原始配置，再检查自己的覆盖项；不为消除报错任意删安全或路由字段。

**策略选择丢失：** 检查当前启用配置和组内选项，按之前的记录恢复一次。显示名称相同不代表底层配置没有变化，需要完成真实任务验证。

**连接正常但退出后断网：** 先通过客户端正常关闭本次启用的系统代理或虚拟接口，再按升级前记录核对残留设置。受管理的代理、VPN 和不认识的网卡不删除。

<a id="rollback"></a>
## 回退条件和旧资料清理

关键任务无法完成、出现未解释的网络副作用，或没有兼容依据时，应先停止扩大迁移。按项目支持的方式退出新版本，并使用可信渠道、兼容的数据备份恢复；不要把新版本已迁移的数据直接交给旧版本强行读取。

旧版本若存在明确安全问题，不把回退当成长期方案，向项目支持确认修复路径或选择仍受支持的版本。本文不推荐任何具体旧安装包。

迁移完成后保留必要的版本与变更记录。备份的保留和删除按自己的恢复需求处理；公开分享问题时只提供最小脱敏样例，不附真实配置。验收应同时包括正常使用和正常退出，不只看启动成功。
